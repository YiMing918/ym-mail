# 佲的邮箱 YM Mail

多用户域名邮箱系统，跑在 Cloudflare 全免费额度上：**游客不用注册就能用临时邮箱收验证码，注册用户认领地址后锁定私有**，全部规则（谁能用哪个域名、能建几个、能不能删、保留多少天）由站长在独立后台 `/admin` 里定。

**[打开站点](https://yxa.us.ci/) · [下载最新版](https://github.com/YiMing918/ym-mail/releases/latest) · [博客部署教程（置顶）](https://bk.ymaym.top/post/ym-mail-guide)**

## 功能一览

| 功能 | 说明 |
| --- | --- |
| 游客临时收码 | 不注册就能领随机地址收信，验证码自动提取、单独成页 |
| 注册认领锁定 | 注册用户认领的地址只有自己能看（连历史邮件一起锁定），公开池和私人邮箱一套系统 |
| 域名 × 人群政策 | 每个域名对注册用户 / 游客分别定：能不能用、自定义和随机各几个、前缀最少几位、能不能删、删后返不返额度 |
| 邀请与奖励 | 邀请码全系统随机生成（批量 1–50 个）；填个人邀请码注册，邀请人得专属额度，可突破政策上限建地址 |
| Gmail 备份转发 | 认领地址的信同时转发一份到用户自己的注册邮箱，站内删了 Gmail 里还有 |
| 自动清理 | 每天凌晨按保留 / 闲置规则批量清理，名额自动返还（细则见下文） |
| 独立后台 | `/admin` 管域名、政策、用户、邀请码、黑名单、发件设置，前台没有任何后台入口 |

怎么跑起来的：

- 收信：Email Routing catch-all → Worker 解析入库 D1，**验证码在收信时就提取好**
- 发信：Resend（免费 100 封/天；注册验证码也走它）
- 会话：存 D1（不用 KV —— KV 写额度是全账号最紧的一档，这套系统一根手指都不碰它）
- 页面：静态资源托管，打开页面不消耗 Worker 请求额度

## 先分清两个地方：GitHub 管代码，Cloudflare 管运行

部署路上你会在两个网站之间来回跑，先把它们分清，后面就不懵了：

| 地方 | 是干什么的 | 本项目在它那儿的东西 |
| --- | --- | --- |
| **GitHub** | 放代码的仓库网站 | 仓库 = 存全部代码；**Actions** = 自动干活的机器人（你一 push 代码，它自动部署、自动检查）；**Releases** = 放发行包的地方（手机部署包 zip 在这下载）；**Secrets** = 仓库设置里的保险柜，存令牌这类不能写进代码的东西 |
| **Cloudflare** | 让项目真正跑起来给人用的平台 | **Workers**（控制台左侧「计算 / Workers & Pages」）= 跑本站代码的地方；**D1**（左侧「存储和数据库」）= 存邮件和用户的数据库；**域名 + DNS** = 收信域名在这托管解析；**Email Routing**（进域名后选「电子邮件」）= 把收到的信转交给 Worker；**API 令牌**（右上角头像 → 我的个人资料）= 给自动部署用的钥匙 |
| **Resend** | 专门负责「发信」的第三方服务 | 只管发注册验证码和用户发信，收信不经过它 |

**一句话理顺**：代码平时躺在 GitHub → 你 push 或点部署，Actions 把代码送到 Cloudflare 的 Worker → 访客打开网站、邮件进来，都由 Cloudflare 处理 → 数据落在 D1 里，哪儿都不去。所以「更新代码去 GitHub，查数据库和域名去 Cloudflare，发不出信去 Resend 看」。

## 部署总览

这个项目有四种部署方式，先看表选一种；不管选哪种，**「部署前共同准备」和「部署后共同收尾」都要做**（建 D1、开邮件路由这些事，部署包和自动部署都不会替你生成）。

| 方式 | 适合什么时候 | 主要用到的东西 | 在哪弄 |
| --- | --- | --- | --- |
| 一、GitHub 自动部署 | 日常更新（推荐） | 本仓库 + 仓库 Secrets 里的部署令牌 | GitHub 仓库页面 |
| 二、wrangler 命令行 | 第一次从零部署、最完整 | 电脑 + Node.js + 本仓库代码 | 电脑终端 |
| 三、手机部署包 | 没电脑、救急、迁移 | 发行版 zip + GitHub App / 手机浏览器 | 手机上 |
| 四、CF 控制台手动 | 临时应急 | CF 控制台 + 解压出的代码文件 | dash.cloudflare.com |

### 四种方式对比（看完就知道选哪种）

| 对比点 | 一、GitHub 自动部署 | 二、wrangler 命令行 | 三、手机部署包 | 四、CF 控制台手动 |
| --- | --- | --- | --- | --- |
| 需要的设备 | 手机或电脑都行 | 必须电脑 | 只有手机也行 | 手机或电脑 |
| 上手难度 | 中（要配一次仓库密钥） | 高（要装软件、敲命令） | 低（下载、上传，就两步） | 低 |
| 第一次大约耗时 | 20 分钟（主要是建 D1、填密钥） | 30 分钟 | 15 分钟（CF 侧没建过要另加） | 10 分钟 |
| 以后更新方不方便 | 最方便：push 一下自动上线 | 一般：每次敲一条命令 | 不方便：每次重新传文件 | 不方便 |
| 出错了好不好排查 | 好：Actions 页有完整日志 | 最好：终端直接报哪行错 | 一般 | 差：控制台提示少 |
| 适合谁 | 部署完还想长期更新的人（推荐） | 有电脑、愿意敲命令的人 | 没电脑救急、把站迁到新账号 | 只改一两个小文件救火 |

**一句话选法**：长期用 → 方式一；第一次部署又想把每一步都看明白 → 方式二走一遍（顺带把 D1 这些都建好）；手边只有手机 → 方式三；线上突然有个小毛病要改 → 方式四。

## 部署前共同准备（四种方式都要）

- **一个 Cloudflare 账号**：建议用相对空闲的账号——免费额度是账号级共用的（细则见「免费额度全清单」），别和一堆高频项目挤一个账号。
- **收信域名**：要先成为这个 CF 账号里的 zone（在别家注册的域名，先把 NS 授权到这个账号）；Email Routing 跟着域名走，域名在哪个账号，收信就只能接哪个账号。
- **发信域名**：必须是**自己注册的域名**（或它的子域名）。免费公共后缀域名（免费领的二级域名）会被 Resend 直接拒绝，收信不受影响、只影响发信。收信和发信可以不是同一个域名。
- **一个 Resend 账号**（要发注册验证码 / 用户发信才需要；只收信可跳过）。
- **想好管理员账号和密码**：后台 `/admin` 用，密码只以哈希形式存为 Worker Secret，不写进任何文件。

## 先搞懂这几把「钥匙」（部署路上会遇到的令牌 / 密钥 / ID 全在这）

部署路上要碰到几样长得像乱码的东西，先在这集中讲清，免得走到一半卡住。每样都讲五件事：是什么、去哪儿弄、填到哪儿、干什么用、要不要保存丢了怎么办。

### 1. Cloudflare API 令牌（CLOUDFLARE_API_TOKEN）

- **是什么**：一串以 `cfat_` 开头的长字符串，相当于给程序用的一把「限权钥匙」——拿着它，程序就能替你操作你的 Cloudflare 账号（但只能干授权过的那几类事，比账号密码安全）。
- **去哪儿弄**：Cloudflare 控制台右上角头像 →「我的个人资料 / My Profile」→「API 令牌 / API Tokens」→「创建令牌 / Create Token」→ 选「编辑 Cloudflare Workers」模板（它自带 Workers、D1 等常用权限），再按部署方式里的说明补上 Email Routing 相关权限 → 创建。
- **填到哪儿**：用方式一/三时，填进 GitHub 仓库的 Secrets（填法在方式一的步骤里）；用方式二时不用它（wrangler 登录走浏览器授权）。
- **干什么用**：自动部署流水线靠它把代码发到你的 Cloudflare 账号、更新 D1。
- **保存与丢失**：**创建成功后只完整显示这一次，关掉页面就再也看不到了**——当场点复制，存进自己的密码管理器或备忘录。万一没存住也不用慌：回令牌列表把这把删掉，重新建一把新的，再把新值换到仓库 Secrets 里即可，站点不受影响。

### 2. 账号 ID（CLOUDFLARE_ACCOUNT_ID）

- **是什么**：你 Cloudflare 账号的编号，一串 32 位字符。它**不是秘密**，就是个门牌号。
- **去哪儿弄**：Cloudflare 控制台首页右侧「账户 ID / Account ID」，点一下就复制；进了任何一个域名，浏览器地址栏里 zone 后面那串也是。
- **填到哪儿**：方式一/三时填进仓库 Secrets。
- **干什么用**：告诉部署流水线「代码要发到哪个账号」——一个邮箱能有多个账号，不指明就发错地方。
- **保存与丢失**：不用特意保存，随时回控制台首页就能查到。

### 3. D1 数据库 ID（D1_DATABASE_ID）

- **是什么**：你建的那个数据库的编号（长得像 `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`），同样**不是秘密**。
- **去哪儿弄**：建 D1 时终端会输出；忘了就去控制台 →「存储和数据库 / D1」→ 点你的库，概览里就有。
- **填到哪儿**：方式一/三填进仓库 Secrets；方式二填进 `wrangler.toml` 文件里。
- **干什么用**：部署时把 Worker 和正确的那个数据库绑在一起，别绑错库。
- **保存与丢失**：不用保存，控制台随时可查。

### 4. 管理员账号和密码（ADMIN_USER / ADMIN_PASSWORD_HASH）

- **是什么**：你登录邮箱后台 `/admin` 用的账号和密码。系统里实际存的是密码算出来的「哈希」（一串指纹），不是密码原文——数据库被看到也还原不出密码。
- **去哪儿弄**：账号自己起（部署时填进 Secret `ADMIN_USER`）；哈希用仓库自带脚本生成：`npm run hash -- '你的密码'`，把输出整串填进 Secret `ADMIN_PASSWORD_HASH`（方式二第 3 步有完整命令）。
- **干什么用**：进后台管域名、政策、邀请码——这是全站权力最大的入口。
- **保存与丢失**：**密码原文一定要自己记牢、存好**（密码管理器 / 记事本）。忘了原文没法找回，只能重走一遍：重新生成新密码的哈希 → 更新 Worker 的 Secret → 重新部署。账号同理，两个都忘了就两个 Secret 一起换。

### 5. Resend API 密钥（RESEND_API_KEY）

- **是什么**：发信服务 Resend 给的钥匙，以 `re_` 开头。
- **去哪儿弄**：Resend 控制台 →「API Keys」→「Create API Key」，权限选 Full access（或 Sending access），创建后复制。
- **填到哪儿**：Worker 的 Secret（`npx wrangler secret put RESEND_API_KEY` 粘进去；方式一步骤里有对应位置）。
- **干什么用**：发注册验证码、用户发信都靠它；没配它，收信不受影响，只是发不出信、注册不了（站内会明确报错，不会默默失败）。
- **保存与丢失**：同样**只显示一次**，当场存好；丢了就回 Resend 删旧建新、换上新值。

### 6. （可选）Telegram 机器人令牌（TG_BOT_TOKEN）

- **是什么**：想让新邮件推送到 Telegram 才需要，是你向 Telegram 的 @BotFather 申请机器人时它给的一串数字加字母。
- **去哪儿弄 / 填到哪儿**：BotFather 对话里 `/newbot` 按提示建机器人拿到令牌；填进 Worker 的 Secret `TG_BOT_TOKEN`，机器人所属对话的 ID 填普通变量 `TG_CHAT_ID`。
- **保存与丢失**：丢了可以让 BotFather 重新生成（旧的自动作废），换上即可。不用推送就整段跳过。

## 方式一：GitHub 自动部署（日常更新就用这个）

**优势**：配好一次，以后每次改代码 push 一下就自动部署、自动检查；部署日志全在 GitHub 上，出错能回看。
**劣势**：第一次要先建令牌、填三个仓库密钥，步骤比其他方式多一点点（下面全拆开写了，照着做就行）。

**要用到的东西**

- 代码侧：本仓库全部文件，自带 `.github/workflows/deploy.yml`（部署流水线：自动生成配置、部署、部署后自检）。
- GitHub 侧：仓库的 **Settings → Secrets and variables → Actions** 里存三个 Secret（只存一次）：`CLOUDFLARE_API_TOKEN`（有 Workers、D1、Email Routing 相关权限的 API 令牌，在 CF 控制台 → 我的个人资料 → API 令牌 里创建）、`CLOUDFLARE_ACCOUNT_ID`（CF 控制台首页右侧能看到）、`D1_DATABASE_ID`（下一步建 D1 时得到）。
- CF 侧：一个已经建好的 D1 数据库（第一次先按方式二的第 2 步建，或在 CF 控制台 → D1 → 创建数据库，名字随意、例如 `ym-mail-db`；建完把它的 ID 填进上面的 Secret）。

**步骤**

1. 把本仓库 fork 或克隆到自己的 GitHub 账号下。
2. 建 D1 数据库（见上），把数据库 ID 填进仓库 Secrets 的 `D1_DATABASE_ID`，另两个 Secret 一并填好。
3. 把代码 push 到 `main` 分支 —— 部署自动开始：在仓库 **Actions** 页能看到进度，绿灯 = 部署成功且自检（请求 `/api/bootstrap`）通过。
4. 接着做「部署后共同收尾」。

**日常更新**：改完代码 push 即可，第 1–3 步都不用重做。

## 方式二：wrangler 命令行部署（第一次从零部署最完整）

**优势**：全程在自己电脑上，每一步都看得见摸得着，报错直接显示是哪一步；建 D1、灌表结构这些事顺手就办了。
**劣势**：要有电脑，还要装 Node.js、敲命令，纯手机党用不了。

**要用到的东西**：一台电脑、Node.js 18+、本仓库代码、CF 账号（`wrangler login` 登录，或用 API 令牌）。

**步骤**

1. 准备代码与依赖：
   ```bash
   npm install
   cp wrangler.toml.example wrangler.toml
   ```
2. 建 D1 并初始化（把命令输出的 `database_id` 填进 `wrangler.toml`）：
   ```bash
   npx wrangler d1 create ym-mail-db
   npm run db:init        # 远程建表（= wrangler d1 execute --remote --file=./schema.sql）
   ```
3. 设置 Secret（在终端里逐个执行，值只进 CF 的密钥存储、不落文件）：
   ```bash
   npx wrangler secret put ADMIN_USER            # 后台管理员账号，自己定
   npm run hash -- '你的管理员密码'               # 生成 PBKDF2 哈希
   npx wrangler secret put ADMIN_PASSWORD_HASH   # 把上一步输出的哈希粘进去
   npx wrangler secret put RESEND_API_KEY        # 发信要用；暂不发信可跳过（发码/发信会返回明确报错，不崩）
   # 可选（Telegram 推送）：npx wrangler secret put TG_BOT_TOKEN；TG_CHAT_ID 是普通变量，写在 wrangler.toml 的 [vars] 里
   ```
4. 部署 Worker：
   ```bash
   npx wrangler deploy
   ```
   记下分配的地址（如 `ym-mail.<你的子域>.workers.dev`）。想用自己的域名访问：在 CF 控制台 → Workers → `ym-mail` → 设置 → 域和路由 → 添加**自定义域**。
5. 接着做「部署后共同收尾」。

## 方式三：手机部署包（没电脑时救急 / 迁移）

**优势**：只有手机也能干；包里就是全部可部署文件，不用装任何软件。
**劣势**：每次更新都要重新下载、重新传一遍；D1、邮件路由这些 CF 侧的东西包里没有，第一次仍要去控制台建。

**要用到的东西**：本仓库**发行版**里的 `ym-mail-deploy-*.zip`（附 `SHA256SUMS.txt` 校验）、GitHub App 或手机浏览器、目标 CF 账号的登录。

**步骤**

1. 到本仓库的 **Releases** 页下最新版 zip，先用 SHA256SUMS.txt 里 的值核对文件完整（手机校验工具任选）。
2. 解压 zip：里面是全部可部署文件（`src/` 代码、`public/` 页面、`schema.sql`、`wrangler.toml.example`），**不含任何数据**。
3. 在 GitHub App / 手机浏览器里打开自己的仓库（还没有就先新建一个空仓库），把解压出的文件逐个上传到仓库根目录（保持目录结构）。
4. 按**方式一**把三个 Secret 配好，上传/push 后自动部署就跑起来了。
5. 注意：D1 数据库、Email Routing 这些 **CF 侧的东西不在包里、也不会自动生成**——第一次迁移到新账号，仍要先在 CF 控制台建好 D1（控制台 → D1 → 创建数据库，再到该库的 Console 里粘贴 `schema.sql` 全文执行建表），然后做「部署后共同收尾」。

## 方式四：Cloudflare 控制台手动部署（临时应急）

**要用到的东西**：CF 控制台、发行版 zip 解压出的文件。

**优势**：不用 GitHub、不用命令行，打开控制台就能改，救火最快。
**劣势**：文件多容易漏，静态页面部分处理不了，只适合临时改一两处。

**说明**：本项目是多文件 Worker（`src/` 下多个模块）+ 静态资源目录，控制台在线编辑器逐个粘贴容易漏文件、静态资源也不好处理，所以这一路**只建议临时应急**（比如改一个小文件救火），正式部署请用方式一或方式二。应急步骤：控制台 → Workers & Pages → `ym-mail` → 编辑代码，把要改的模块文件内容替换掉 → 保存并部署；D1、Secret 等绑定在 Worker 的「设置」页里改。

## 部署后共同收尾（四种方式都要做一遍）

### 1. 每个邮箱域名开 Email Routing（每个域名做一遍）

在哪弄：CF 控制台选中该域名 → **Email（电子邮件）→ Email Routing**。

1. 启用 Email Routing（它会自动加好 MX / TXT 记录）；
2. 「目标地址」里添加并**验证**站长自己的常用邮箱（后面的备份转发要用；验证邮件点一下链接即可）；
3. 「路由规则」→ **Catch-all** → 操作选 **发送到 Worker** → 选 `ym-mail` → 保存。

### 2. 在 Resend 验证发信域名（要发码 / 发信才做）

在哪弄：Resend 控制台 → Domains；DNS 记录加在 CF 控制台 → 该域名 → DNS。

添加发信域名 → 按 Resend 给的清单把 DKIM / SPF 等记录加到该域名的 DNS 里 → 等状态变成 **Verified**。不验证 Resend 会拒发，接口会把拒绝原因原样提示。再提醒一次那个实测大坑：**发信域名不能用免费公共后缀域名**，收信用免费域名、发信用自己域名子域名（如 `mail.你的域名`）完全可以，后台「系统发件地址」填子域名下的地址即可。

### 3. 管理员初始化

1. 打开 `https://<你的地址>/admin`，用部署时设的管理员账号密码登录；
2. 在「域名政策」里**添加你的域名**（第一个添加的自动成为主域名，不可删除）；
3. 按需要调政策：哪个域名开放给注册用户 / 游客、各自能建几个、游客保留天数、注册方式等（每项的含义后台里都有白话说明）；
4. 回到前台，用自己的常用邮箱**注册第一个账号** —— 系统会自动把第一个注册账号标记为站长账号（不受个数 / 位数政策限制）。**第一个账号不需要邀请码、也不需要邮箱验证码，任何注册方式（包括关闭注册）都不会挡第一个账号**——这是故意的，保证刚部署完没人会被自己的注册门锁在外面；从第二个账号开始，注册方式才按后台设置生效。邀请码只有一个输入框：填站长发的注册码 = 直接注册、只享政策额度；填已注册用户的个人邀请码 = 也能注册，且邀请人得专属额度（开关和个数在后台）。认领自己的主地址后，在 D1 里把它的 `protected` 置 1 可防误删：
   ```sql
   UPDATE addresses SET protected = 1 WHERE address = '你的主地址';
   ```
5. 备份转发还差一步：每个开了备份转发的用户，其**注册邮箱**都要先在 Email Routing 的「目标地址」里验证过，转发才会成功（未验证时只会在日志里失败，不影响收信入库）。

### 4. 上线自检

- [ ] 往任意地址（如 test@你的域名）发一封带验证码的测试信 → 前台能看到、验证码自动提取
- [ ] 游客模式：不登录能生成临时地址、能看公开邮件
- [ ] 注册一遍（邮箱验证码能收到 / 邀请码能用）
- [ ] 认领一个公开地址 → 退出登录后看不到它的信
- [ ] 后台改一条政策 → 前台额度显示跟着变（最长 60 秒缓存延迟）
- [ ] 第二天看一眼 cron 有没有按保留天数清理（或等几天抽查）

## 免费额度全清单（都是什么、有多少、超了会怎样、这套系统怎么花）

这套系统只用四家的免费额度：Cloudflare Workers、D1、Email Routing、Resend。先说清一个大前提：**Cloudflare 的免费额度大多是「账号级」的——同一个账号下所有 Worker/D1 共用一池**，所以本站建议部署在一个相对空闲的账号里，别和一堆高频项目挤。另外所有「每天」的额度都在 **UTC 0 点（北京时间早上 8 点）重置**。

### 1. Workers 请求：100,000 次/天（账号级）

- **干啥的**：每调用一次 Worker 算一次。本站的页面是静态资源（不算，见第 3 条），只有接口调用算：打开站点拉一次首屏数据、点开一封信、登录、注册、建地址等。
- **超了会怎样**：当天的新请求直接报错（不会扣费，免费版没有超量付费这一说），第二天早上 8 点恢复。
- **本站怎么省**：首屏把数据打包成一次请求；列表只拉摘要、正文点开才拉；30 秒一次的自动刷新只问一句「有没有新信」（一条聚合查询），没新信就不拉列表。一个人正常用，一天也就几百次请求；10 万次够几百个活跃用户。

### 2. Workers CPU：10 毫秒/次请求（免费版）

- **干啥的**：每次请求里代码真正算题的时间（等数据库、等网络不算）。
- **超了会怎样**：这次请求失败。本站最重的活是收信时解析邮件正文 + 正则提验证码，都是毫秒内的小活，离上限很远。

### 3. Workers 静态资源：免费不限量

- **干啥的**：本站的前台页面、后台页面、样式和脚本都走静态托管，打开页面本身**不占**上面 10 万次请求额度。这是本站能「随便刷」的原因——贵的是接口调用，不是看页面。

### 4. D1 读：5,000,000 行/天（账号级）

- **干啥的**：数据库查询扫到多少行算多少行。本站所有数据——用户、地址、邮件、会话、设置、政策——都在 D1 里（见第 6 条为什么不用 KV）。
- **超了会怎样**：当天查询报错，次日恢复。
- **本站怎么省**：列表查询只取摘要列且分页（一页 30 条）；设置/政策/黑名单在进程内缓存 60 秒，收信和接口不反复查；自动刷新用一条聚合 SQL 拿全站未读数，不逐箱数。

### 5. D1 写：100,000 行/天 + 存储 5 GB（账号级）

- **干啥的**：每插入/更新/删除一行算一次写。收信最花写：一封信 = 邮件 1 行 + 每个附件 1 行 + 地址活跃时间更新 1 次；登录写 1 行会话；注册写 1 行用户。
- **超了会怎样**：当天写不进去（收信会失败重试、注册会报错），次日恢复；存储满了同样写不进，靠每天的自动清理腾地方（见「自动清理机制」一节）。
- **本站怎么省**：正文最多存 10 万字；附件单个 ≤512KB 才存（大的只留文件名）；黑名单/被封地址的信在写库之前就拦掉，一行都不写。

### 6. KV：本站**完全不用**（这条是故意写给部署者看的）

- **为什么躲着它**：KV 免费版每天只有 **1,000 次写（账号级，所有项目共用）**，是 Cloudflare 全家桶里最紧的额度。很多同类项目把会话、计数器放 KV，几百个用户就能写爆，还连累同账号的其他项目。
- **本站的做法**：会话、设置、验证码、限流计数全部放 D1（写额度 10 万/天，是 KV 的 100 倍），从根上避开这个坑。

### 7. Email Routing（收信通道）：免费，无公布的每日收信量上限

- **干啥的**：负责把发到你域名任意地址的信转给 Worker。本站每个域名只占一条 catch-all（全域接收）。
- **相关的量**：每个域名最多 200 条普通路由规则（catch-all 不占这个数）；**每个账号最多 200 个「已验证目标地址」**——本站的「Gmail 备份转发」就是往用户注册邮箱转发，目标地址要先在账号里验证过，200 个封顶，意味着靠转发备份的用户最多约 200 人（站内收信本身不受这个限制）；单封邮件上限 25 MB，超了对方会收到退信。

### 8. 定时任务（Cron）：免费

- 本站每天只跑 **1 次**（UTC 19:15 = 北京时间凌晨 03:15），一次批量做完全部清理，不额外花什么额度。清理细则见下一节。

### 9. Resend（发信通道）：100 封/天，3,000 封/月

- **干啥的**：本站自己不能发信（Email Routing 只收不发），注册验证码和用户发信都经 Resend 发出。
- **超了会怎样**：当天/当月发不出，注册的人收不到验证码。这是全系统最先见底的一项，人多了先升它或换通道。
- **一个大坑（实测）**：Resend 的发信域名**必须是自己注册的域名**，免费公共后缀域名（各种免费领的二级域名，如 `.us.ci`、`.eu.cc` 这类）会被直接拒绝（"We don't allow free public domains"）。所以：**收信域名可以用免费域名，发信域名请用自己买的正经域名**（用它的子域名也行，如 mail.你的域名，不影响主域名现有服务）。

### 10. GitHub Actions（自动部署）：公开仓库免费不限量

- 推代码自动部署靠它。公开仓库的标准运行器免费不限分钟数；私有仓库免费版每月 2,000 分钟（一次部署约 40 秒，怎么都够）。本站仓库是公开的，不用管这项。

### 自查方法

- 请求数：Cloudflare 控制台 → Workers & Pages → 用量；
- D1 读写量：控制台 → D1 → 选库 → Metrics；
- 站内规模：邮箱后台顶部有用户数 / 邮箱数 / 今日收信三个数；
- Resend 用量：Resend 控制台首页直接显示当月已发/剩余。

## 自动清理机制（清什么、按什么规矩、在哪改）

每天北京时间凌晨 03:15 自动跑一次，一批批量 SQL 做完下面全部清理。**所有天数都是站长在后台自己填的数字**，下面写的是默认值和规则：

| 清什么 | 规则 | 在哪改 |
|---|---|---|
| 游客的邮件 | 超过「游客保留天数」（默认 1 天）的全删，附件一起删；游客没有星标豁免 | 后台 → 全站开关 → 游客保留天数 |
| 注册用户的邮件 | 按**每个用户自己选**的保留天数删（在他的个人设置里选）；站长设的「最长保留」封顶：用户选了永久或超过上限的，一律按上限算；**星标邮件永不删**；附件随邮件一起删 | 后台 → 保留与清理 → 注册用户最长保留（默认上限 180 天） |
| 闲置的**随机**地址 | 随机地址超过「闲置清理天数」（默认 7 天）没收到新信 → 地址连同它的全部邮件、附件一起删，名额自动返还；**从没收到过信的按建立时间算**（领了不用也不会永久攒着）；用专属额度建的随机地址被清时，**专属额度退回主人**；**自定义地址永不被这条清** | 后台 → 域名政策/清理设置 → 随机地址闲置清理天数 |
| 没用的游客邮箱（手动） | 等不及每天凌晨那一趟时：后台「清理没用的邮箱」一键检测/删除——游客领了却从没收到过信、且建好超过 30 分钟的临时邮箱（刚建的留缓冲）；收到过信的、被认领的一律不碰 | 后台 → 清理没用的邮箱 → 检测 / 一键删除 |
| 过期的注册验证码 | 过期即删（验证码本身 10 分钟有效） | 不用管 |
| 过期的登录会话 | 过期即删 | 不用管 |
| 陈旧的限流记录 | 7 天前的登录失败计数等记录删掉 | 不用管 |

不自动清、需要人工管的：

- **墓碑记录**：用户删掉地址且该域名政策是「删后不返还额度」时，会留一条墓碑继续占着名额（防有人反复删了重建、抢注好名字）——这是故意的，不是垃圾数据；想放行就在后台把该域名的「删掉后返还额度」打开，之后删的就不再占额。
- **黑名单 / 封禁名单**：后台手动加减，不自动过期。
- **已删域名的存量数据**：在后台删域名只是停用，旧地址和旧邮件保留在库里（防误删），重新添加同名域名即恢复。

## 探活（站点还活着吗，谁在探、探什么、在哪看）

**探活需要什么**：一个能定时发请求的东西。本站的探活分工是站长的测活总览 **ym-dash** 在探——它有一个独立的探活 Worker，每 30 分钟自动把总览里的站点挨个请求一遍，结果记在 KV 里、总览页上直接看每个站「正常 / 异常 + 响应毫秒数」。

**怎么给本站加探活**（在哪弄：ym-dash 后台 → 站点管理 → 添加）：

1. 名称随便填（如「邮箱」），URL 填本站主域名根地址；
2. 保存后点一次「立即检测」确认能通（返回 200、几百毫秒内）；
3. 之后每 30 分钟自动探，结果在 ym-dash 总览页看。

**探什么才算真活**：

- 探**首页**返回 200 —— 只能说明静态页面还在（页面是静态托管，Worker 挂了首页照样开）；
- 探 **`/api/bootstrap`** 返回 200 且是 JSON —— 这才是 Worker 和 D1 都通的深层标准。本仓库的自动部署流水线每次部署完都会探这个地址做自检，探不过这次部署就算失败。

## 保活（需不需要定期弄点动静防休眠）

**结论：核心服务不需要保活。** Workers、D1、Email Routing 都没有休眠机制，不需要定期登录或发请求去"叫醒"；域名证书由 Cloudflare 自动续。真正需要人工盯的只有三件：

1. **邮箱域名到期续费**：域名过期收信立刻断；免费领的域名尤其注意，很多没有到期宽限期、过期直接删除——提前续，别卡最后一天；
2. **Resend 的 API 密钥别误删**：删了发信和注册验证码立刻停，站内会给出明确报错，重建一把新 key 换上即可；
3. **GitHub 仓库别长期荒废**：GitHub 会停用长期无活动仓库的 Actions 定时触发。本站部署是 push 触发、每日清理是 Cloudflare 自己的 Cron，这两件都不靠 GitHub 定时，所以影响很小；仓库页面顶部若出现定时工作流被停用的提示，点一下重新启用即可。

## 自动更新（什么在自动跑、靠谁触发、坏了怎么办）

| 自动的事 | 靠谁触发 | 频率 | 在哪看 / 怎么手动弄 |
| --- | --- | --- | --- |
| 代码部署 | push 到 main 触发仓库的 deploy.yml | 每次 push | GitHub 仓库 → Actions 页看绿灯；手动：Actions 页选 deploy 工作流 → Run workflow |
| 部署后自检 | 同上流水线最后一步探 `/api/bootstrap` | 每次部署 | 同上，红灯就是部署或站点有问题，先看这一步的日志 |
| 数据清理 | Cloudflare Cron（UTC 19:15） | 每天 1 次（北京时间 03:15） | 细则见「自动清理机制」；CF 控制台 → Workers → ym-mail → 触发器 能看到这个 Cron |
| 证书续期 | Cloudflare 自动 | 到期前自动 | 不用管 |

本站没有上游依赖，不存在"跟上游合并更新"这一环；要升级就是改代码 push 一次。

## 出事了怎么办（东西丢了 / 坏了 / 删了：后果 + 能不能重建 + 怎么重建）

不光是钥匙——这个系统里每样东西出事的后果都不一样，先看总表，再按条目找重建步骤。**先记一条总原则：数据只存在 D1 里，代码和配置都能重建，唯独 D1 里的数据没了就是没了。**

| 出事的东西 | 后果 | 能重建吗 |
| --- | --- | --- |
| D1 数据库被删 | 全部邮件、用户、地址、政策**永久消失** | ❌ 数据不可恢复，只能建空库从零开始 |
| 域名过期没续上 | 收信全断、网站打不开 | ⚠️ 宽限期内续费可恢复；被别人抢注 = 永久丢失 |
| Email Routing 被关 / 规则被删 | 信进不来，发信方收到退信，期间的信**找不回** | ✅ 重新开启并指回 Worker |
| Worker 被删 | 网站打不开、收信中断 | ✅ 重新部署即可，数据在 D1 不受影响 |
| 管理员密码忘了 | 进不了后台（前台收发信不受影响） | ✅ 换新哈希 Secret 后重新部署 |
| CF API 令牌 / Resend 密钥丢了 | 自动部署停 / 发不出信 | ✅ 删旧建新，换上即可 |
| 每日清理的 Cron 没了 | 不自动清理，邮件和附件越积越多、慢慢占满 D1 | ✅ 控制台给 Worker 加回触发器 |
| 自定义域被删 | 只能用 workers.dev 的备用地址打开 | ✅ 控制台重新添加 |
| GitHub 仓库被删 | 代码没了；**CF 上的站还在跑，不受影响** | ✅ 用发行包 zip 重建仓库，Secrets 要重配 |

<details>
<summary>点开看每种情况的重建步骤</summary>

**D1 数据库被删（最严重，先看预防）**
- 后果：邮件、用户、地址、邀请码、政策全部归零，没有任何官方恢复通道。
- 预防（重要）：养成定期导出的习惯——CF 控制台 →「存储和数据库 / D1」→ 你的库 →「导出」，把 SQL 文件存好；或本地 `npx wrangler d1 export ym-mail-db --remote -o backup.sql`。
- 真删了怎么办：重建一个新库（方式二第 2 步）→ 灌 `schema.sql` → 把新库 ID 更新到 `wrangler.toml` / 仓库 Secrets → 重新部署 → 重新开 Email Routing 不受影响（路由指向 Worker，与库无关）→ 第一个注册的账号重新成为站长，域名政策要重新配一遍。导出的备份可用 `wrangler d1 execute --remote --file=backup.sql` 导回。

**域名过期**
- 后果：DNS 失效，收信、网站、Resend 发信验证会陆续全断。
- 怎么办：还在宽限期（各注册商不同，免费域名很多**没有宽限期**）就立刻续费，恢复后什么都不用改；已经掉出被别人注册走了，只能换新域名：新域名加进 CF 并开 Email Routing、后台「域名政策」里添加新域名并设为主域名、Resend 重新验证发信域名——用户原来的地址全部作废，要提前通知。

**Email Routing 被关 / catch-all 规则被删**
- 后果：这段时间的来信会被对方服务器退回或丢弃，**事后补不回来**。
- 怎么办：按「部署后共同收尾」第 1 步重新启用并把 catch-all 指回 `ym-mail` Worker，几分钟内恢复收信。

**Worker 被删**
- 数据在 D1 里，不受影响；但删的这段时间网站打不开、收信也会中断（路由找不到 Worker）。
- 怎么办：重新部署（方式一 push 一次 / 方式二 `wrangler deploy`）→ 回 Email Routing 看 catch-all 是否还指着它，被清掉就重新指一次。

**管理员密码忘了**
- 前台和收发信都不受影响，只是进不了后台。
- 怎么办：本地 `npm run hash -- '新密码'` 生成新哈希 → `npx wrangler secret put ADMIN_PASSWORD_HASH` 换上 → 重新部署一次，用新密码登录。

**Cron 触发器没了**
- 短期无感，长期邮件和附件越堆越多，直到 D1 写满开始报错。
- 怎么办：CF 控制台 → Workers → `ym-mail` →「触发器 / Triggers」→ 添加 Cron `15 19 * * *`（UTC，即北京时间 03:15）。

**GitHub 仓库被删**
- 线上站点照常跑（代码已经在 CF 上了），但没法再 push 更新、自动部署停摆。
- 怎么办：新建仓库 → 把发行版 zip 解压上传 → 仓库 Secrets 三件套重新配一遍 → push 触发一次部署验证。

</details>

## 安全提醒（什么绝不能给别人）

- **管理员账号密码、六把钥匙里的任何一样，都不能发给任何人、不能出现在截图里**。要给人看截图，先把地址栏里的域名、后台里的账号名打码。
- **后台地址 + 管理员密码 = 全站最高权限**：拿到的人能看所有未被认领的邮件、改政策、发邀请码。密码别和别的网站共用，建议存进密码管理器。
- **GitHub 和 Cloudflare 两个账号都建议开两步验证**（账号设置 → 安全 / 两步验证）：这两个账号是总闸，丢了它们，这个站就归别人了。
- 收信域名别乱借给别人建地址：谁的地址收到什么信，在公开池规则下是可能被别人看到的（认领锁定的除外）。
- Resend 密钥、CF 令牌万一不小心发出去了（比如贴进了公开页面）：别犹豫，回对应控制台**删掉旧的、重建新的**换上，旧的作废就不怕了（步骤在钥匙那一节）。

## 术语速查（全文黑话都在这）

| 词 | 人话解释 |
| --- | --- |
| Worker | 跑在 Cloudflare 上的一段代码，就是本站的「大脑」，收信、网页接口都由它处理 |
| Pages | Cloudflare 放网站的服务，本站页面是静态文件、由 Worker 一起托管，没单独用 Pages |
| D1 | Cloudflare 的数据库服务，本站的邮件、用户、政策都存这里 |
| KV | Cloudflare 的另一种存储（键值对），**本站没用它**，就是为了省它那点紧巴巴的免费额度 |
| zone | 一个域名在 Cloudflare 里的「地盘」，DNS 解析托管过来了才算一个 zone |
| NS 授权 | 把域名的解析大权从注册商交给 Cloudflare，在注册商那改两个 NS 地址 |
| Email Routing | Cloudflare 的收信服务：把寄到你域名的信按规则转交给 Worker 或你的常用邮箱 |
| catch-all | 「全收」规则：寄到这个域名任意地址的信都接住，不用逐个地址配 |
| Secret | 存在平台保险柜里的秘密值（密码哈希、密钥），代码里看不到、日志里也不显示 |
| 绑定 | 把数据库这类资源「接线」到 Worker 上，代码里用约定的变量名（如 DB）使用它 |
| Cron / 触发器 | 定时闹钟，到点自动叫 Worker 干一次活（本站每天清一次数据） |
| wrangler | Cloudflare 官方的命令行工具，在电脑上部署 Worker、管 D1 都用它 |
| push | 把本地代码提交上传到 GitHub 仓库的动作，方式一靠它触发自动部署 |
| fork | 把别人的 GitHub 仓库复制一份到自己账号下 |
| 哈希 | 密码算出来的指纹，能验证密码对不对，但从指纹反推不出密码原文 |

## 它跟同类有什么不同

- **认领锁定**：临时邮箱地址人人可见，但谁注册认领了就变私有（连历史邮件一起锁定），一个系统同时当公开临时邮箱和私人邮箱用。
- **政策细到域名 × 人群 × 地址种类**：每个域名对注册用户/游客分别定自定义与随机的个数、自定义前缀最少位数、能否删除、删后返不返额度。
- **验证码是一等公民**：收信即提取、独立验证码页、TG 推送里直接带码。
- **为免费额度而写**：不用 KV、设置全缓存、列表只拉摘要、清理一天一次批量 SQL。

## 优点

- 全免费跑（Cloudflare 免费额度 + Resend 免费档），无服务器、无月租。
- 部署物只有一个 Worker + 一个 D1 + 静态文件，迁移 = 换账号重跑部署清单。
- 代码与数据分离：仓库里没有任何域名、账号、用户数据；域名全部在后台动态管理。

## 缺点 / 已知限制（使用层面）

- **发信总量受 Resend 免费档限制**（100 封/天）：注册高峰时验证码可能排队，超了当天发不出。
- **发信域名不能用免费公共后缀域名**：Resend 会拒绝（收信不受影响）；发信请用自己注册的域名或其子域名。
- **备份转发有个前置条件**：转发目标（用户注册邮箱）必须先在 Cloudflare Email Routing 的目标地址里人工验证，陌生用户注册后不会自动完成，需要站长协助或用户配合点验证链接；没验证的就只有 TG/站内能看。
- **游客额度是全站共用一池**（和预览一致）：游客把某域名的随机地址占满后，其他游客在该域名就建不了新的，要等闲置清理或站长放宽。
- **HTML 邮件是沙箱 iframe 渲染**：个别排版怪异的营销邮件显示可能不完美；正文过长会截断（10 万字）。
- **附件只存 ≤512KB 的**：大附件只保留文件名信息，正文里会注明未保存。
- **改政策有最长 60 秒的跨实例延迟**：后台改完，本实例立刻生效；其他边缘实例最迟 60 秒内跟上（正常使用无感）。
- **删域名是停用不是清除**：存量地址和邮件保留在库里（防误删丢数据），重新添加同名域名即可恢复可见。

## 本地开发

```bash
npm install
cp wrangler.toml.example wrangler.toml        # database_id 本地可保留占位
# .dev.vars 里写本地用的 ADMIN_USER / ADMIN_PASSWORD_HASH（参考 README 第 3 步生成哈希）
npm run db:init:local
npm run dev                                     # http://localhost:8787，前台与 /admin 都可开
```
本地 `wrangler dev` 不会真的投递邮件（Email Routing 是线上功能）；收信链路的验证方式见 NOTES.md。需要 wrangler 4.x（`run_worker_first` 数组写法）。
